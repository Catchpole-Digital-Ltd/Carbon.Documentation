# Bridge Protocol Specification

The Bridge protocol is a binary WebSocket protocol for communication between clients and Carbon-enabled Rust servers. It provides efficient, structured remote procedure calls (RPCs) for server administration.

## Protocol Overview

| Property | Value |
|----------|-------|
| Transport | WebSocket (ws:// or wss://) |
| Encoding | Binary (little-endian) |
| Authentication | Password in URL path |
| Message Type | RPC-based request/response |

## Connection

### URL Format

```
ws[s]://<address>:<port>/<password>
```

| Component | Description |
|-----------|-------------|
| `ws://` | Insecure WebSocket |
| `wss://` | Secure WebSocket (TLS) |
| `address` | Server hostname or IP |
| `port` | Bridge port (typically RCON port + 1) |
| `password` | RCON password |

### WebSocket Configuration

```
Binary Type: arraybuffer
Subprotocol: None
```

## Binary Data Types

All multi-byte values use **little-endian** byte order.

### Primitive Types

| Type | Size | Description |
|------|------|-------------|
| `int8` | 1 byte | Signed 8-bit integer |
| `uint8` | 1 byte | Unsigned 8-bit integer |
| `int32` | 4 bytes | Signed 32-bit integer |
| `uint32` | 4 bytes | Unsigned 32-bit integer |
| `int64` | 8 bytes | Signed 64-bit integer |
| `uint64` | 8 bytes | Unsigned 64-bit integer |
| `float` | 4 bytes | IEEE 754 single-precision |
| `double` | 8 bytes | IEEE 754 double-precision |
| `bool` | 1 byte | 0 = false, 1 = true |

### String Types

#### Length-Prefixed String
```
[uint32: byte_length] [bytes: utf8_data]
```

#### 7-Bit Encoded String
```
[7BitEncodedInt: byte_length] [bytes: utf8_data]
```

The 7-bit encoding compresses small lengths:
- Values 0-127: 1 byte
- Values 128-16383: 2 bytes
- And so on...

#### Null-Terminated String
```
[bytes: utf8_data] [uint8: 0x00]
```

#### Fixed-Length String
```
[bytes: utf8_data (padded with nulls to fixed length)]
```

### Byte Arrays
```
[bytes: raw_data (length known from context)]
```

## Message Format

All messages follow this structure:

```
┌──────────────────┬───────────────────┬────────────────────┐
│   Message Type   │      RPC ID       │      Payload       │
│     (int32)      │     (uint32)      │    (variable)      │
└──────────────────┴───────────────────┴────────────────────┘
```

### Message Types

| Value | Description |
|-------|-------------|
| 0 | RPC message |

### RPC ID Generation

RPC IDs are generated by MD5 hashing the RPC name with a prefix:

```
RPC_ID = MD5_UINT32_LE("RPC_" + RpcName)
```

The hash is computed as:
1. Concatenate `"RPC_"` with the RPC name (e.g., `"RPC_ServerInfo"`)
2. Compute MD5 hash (16 bytes)
3. Extract first 4 bytes as little-endian uint32

## Connection Lifecycle

### Handshake Sequence

```
┌────────┐                              ┌────────┐
│ Client │                              │ Server │
└───┬────┘                              └───┬────┘
    │                                       │
    │ ──── WebSocket Connect ─────────────> │
    │      ws://host:port/password          │
    │                                       │
    │ <─── WebSocket Accept ─────────────── │
    │                                       │
    │ ──── RPC: ServerInfo ───────────────> │
    │ ──── RPC: CarbonInfo ───────────────> │
    │ ──── RPC: Players ──────────────────> │
    │ ──── RPC: Plugins ──────────────────> │
    │ ──── RPC: ConsoleTail(200) ─────────> │
    │ ──── RPC: ChatTail(200) ────────────> │
    │ ──── RPC: AccountPermissions ───────> │
    │                                       │
    │ <─── RPC Responses ────────────────── │
    │      (binary frames)                  │
    │                                       │
```

### Streaming Updates

After initial handshake, the server pushes updates:

| RPC | Trigger |
|-----|---------|
| `ConsoleLog` | New console output |
| `ChatLog` | New chat message |
| `RequestMapEntities` | Polled every ~1 second |

## Error Handling

The protocol does not define explicit error responses. Errors are typically:

1. Returned via `ConsoleLog` RPC as error messages
2. Indicated by empty or malformed responses
3. Connection closure for authentication failures

## Keepalive

Clients should periodically poll to maintain connection:

| RPC | Interval | Purpose |
|-----|----------|---------|
| `ServerInfo` | ~10 seconds | Refresh server status |
| `Players` | ~10 seconds | Refresh player list |
| `RequestMapEntities` | ~1 second | Update map positions |

## Implementation Notes

### RPC ID Calculation

```python
import hashlib
import struct

def get_rpc_id(name: str) -> int:
    data = f"RPC_{name}".encode('utf-8')
    md5_hash = hashlib.md5(data).digest()
    return struct.unpack('<I', md5_hash[:4])[0]

# Example:
# get_rpc_id("ServerInfo") -> 0x12345678
```

### Byte Order

All multi-byte integers use **little-endian** byte order:

```
uint32 value = 0x12345678
Bytes: [0x78, 0x56, 0x34, 0x12]
```

### String Encoding

All strings use UTF-8 encoding with a 4-byte (uint32) length prefix:

```
string "Hello" (5 bytes)
Bytes: [0x05, 0x00, 0x00, 0x00, 'H', 'e', 'l', 'l', 'o']
```

### Nullable Fields

Optional fields use a boolean prefix:

```
bool      HasValue
// If true:
<field_type> Value
```
